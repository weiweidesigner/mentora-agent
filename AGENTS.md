# Veya agent instructions

- Preserve the general agent reasoning loop for every request. Optimize execution infrastructure (stream transport, same-turn read caching, deduplication, artifact loading, and model-selected independent calls) without replacing reasoning with domain-specific fast paths, fixed data universes, report templates, forced research/delivery phases, tool-count budgets, or synthetic fallback answers. The agent decides scope, tools, validation, revisions, and when the requested work is complete; user cancellation and the runtime's overall timeout remain authoritative.

- Yahoo market-data tools are removed. Do not invoke yahoo-data, yfinance, Yahoo quote/fundamental APIs, or restore Yahoo fallback providers. Use the remaining source tools and disclose unavailable data.

- General web/news discovery uses the provider route documented by `external-search`: Tavily first and Serper as the automatic fallback. Kimi remains available through an explicit source choice. Keep AInvest internal articles, structured market data, and user-requested URL reading as separate capabilities. Preserve the selected provider and failed attempts in the result instead of hiding routing failures.
- Reuse successful observations within the turn. A partial batch is usable: retain successful rows and narrow only an essential missing field instead of refreshing the whole universe. After a successful discovery search, do not direct-fetch its result pages to reconfirm the same fact; one narrower follow-up search is enough when an essential date or field is missing. Treat blocked or failed direct URL reads as terminal for that route and continue from available evidence.
- Network discovery and URL reading must use the matching project skill. Do not create inline Python, Node, `curl`, or `wget` requests to probe third-party URLs, reverse-engineer forms, vary symbols or user agents, or bypass an unsupported market-data contract. Inline code may transform local files already produced by a skill. An HTTP 4xx/5xx response, browser-verification/CAPTCHA page, or HTML response where structured data was expected ends that source route for the turn; switch once to a different documented skill/provider or disclose the limitation.

- For financial research, market data, charts, uploaded-chart analysis, AInvest actions, calculations, search, or final investment interpretation, select the matching project skills under `.agents/skills` before acting. When the host prompt explicitly says that it already pre-resolved the execution path and provides the exact scripts and contracts, treat those named skills as selected and use the supplied contracts directly instead of rereading their bridge or canonical `SKILL.md` files.
- For a requested imaginative image or illustration, use the `flux-image` project skill. Its output is artwork, not a data chart or financial evidence.
- A project skill is a discovery bridge. After selecting it, read its canonical `app/skills/<skill>/SKILL.md` completely and resolve scripts, schemas, references, and assets relative to that canonical directory.
- Do not replace an available Veya skill with an ad-hoc implementation. Follow its routing constraints, market scope, schema-first requirements, CLI allowlists, and output contract.
- Treat the native business `kline.py` as an available cross-asset component for equities, ETFs, crypto pairs, and data-source-resolvable option contracts. Select it when its OHLCV and technical channels best answer the question; select a generic chart when its visual form better fits the requested data or comparison. Do not use company financial, valuation, rating, dividend, ownership, or insider modules for crypto or option contracts.
- For Shanghai/Shenzhen stock or index minute/intraday prices, select `ashare-minute`: Eastmoney supports a rolling recent-five-session window, with explicit exchange identity and no server quote cache. It is separate from Fuyao daily data and the generic AInvest K-line source.
- For mainland A-share data, `a-share-data` provides Fuyao historical daily OHLCV through the existing K-line component, raw batch or paged market snapshots, and a monthly trading calendar. Check each script's asset, interval, and API-key contract before selecting it; use other data/chart skills when the requested scope differs.
- Compose skills when needed: data/search first, transformation second, chart rendering third, and visual validation when applicable. The active Agent writes the final evidence-grounded answer directly; do not discover or call a separate text-generation skill.
- For large CSV, JSON, XLS, or market-history datasets, download or copy the source to `outputs/` and let the matching local Python skill read the file. Never fetch a large raw dataset into model context or manually reason over all of its rows. Consolidate calculations and statistical tests into one deterministic execution when practical.
- Run registered data, search, calculation, and rendering scripts through `app/skill_runner.py execute`. Treat `dataHandoffs[].summary` as the reasoning observation and pass `dataHandoffs[].path` downstream. Do not reopen or print a complete artifact unless that summary lacks a field explicitly required by the user.
- Evidence is sufficient when a successful deterministic result covers the requested sample, definitions, key statistics, and limitations. Move directly to the deliverable at that point. Do not reopen the result, recompute the same metric, add an unrequested subsample or robustness cut, or seek corroboration merely to confirm it again. Add another step only for a concrete contradiction, failed execution, or a missing user-required field.
- For an HTML research report, render once and perform one bounded validation pass. Use additional screenshot or vision review only when the user explicitly asks for pixel-level visual QA or when the first validation finds a concrete defect. Do not repeatedly tune wording, individual table cells, or responsive styles after the report already satisfies the requested evidence and layout.
- For first-party business and generic chart components, a successful renderer exit, a non-empty HTML artifact, and the absence of reported runtime errors are the normal validation. Do not create a screenshot or call `read_image` solely to inspect a standard component. Use screenshot or vision review only when the user explicitly requests visual QA or a concrete rendering defect is already indicated. Treat QA screenshots as intermediate files; never emit them through `AIME_FILE` or `AIME_CHART`.
- Use an evidence-first, text-and-visual analysis style. When trustworthy structured data supports a time series, comparison, ranking, composition, distribution, K-line, fund-flow, event sequence, or relationship view, choose chart skills and chart count according to the user's question and the data.
- Every visual must support a specific conclusion and should appear next to its interpretation. Explain the most important change, difference, or inflection instead of repeating every plotted value. Use multiple visuals when they answer distinct questions.
- Do not force a visual for a single scalar, simple status, action result, insufficient evidence, or a case where a chart would mislead. Clearly disclose stale, incomplete, proxy, or degraded data.
- Before rendering, read the selected chart skill's exact schema/CLI contract. After rendering, verify that the standalone HTML exists and is non-empty; use visual validation for complex or visually risky outputs.
- Generated user-facing HTML belongs in `outputs/generated/`. Include each chart at the relevant point in the final answer as `[[AIME_CHART:/absolute/path/to/chart.html]]` on its own line.
- Emit `AIME_FILE` for HTML only when the HTML was produced through the `streamviz` skill. Other chart HTML is an inline visualization and must not be offered as a file download. Non-HTML deliverables may still use `AIME_FILE` when the user-facing file is complete.
- Never claim an account or chart action succeeded unless the relevant skill executed it and its required verification passed.
