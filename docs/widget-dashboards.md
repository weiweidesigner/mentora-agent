# Widget dashboards

Open the sidebar Widget entry or `?tab=widgets`. A dashboard is a 12-column canvas with a 24px vertical unit and 20px card gaps. Drag a card header to move it, or its lower-right corner to resize. On small screens the cards stack at full width; vertical size and order remain editable. Header arrow keys move cards and resize-handle arrow keys change dimensions. The minus/plus controls adjust width. Colliding cards move down when an edit ends.

The wider left pane is the Mentora Widget assistant conversation. Browser-style tabs above the canvas switch independent dashboards, with a plus button to create one. Each dashboard retains its own bounded chat history and selected-card scope; recent turns accompany follow-up model requests. Selecting a board shows its canvas and name in the right pane; rename and delete actions live in that pane. Theme, sidebar-collapse controls, and recent chats are hidden while viewing Widget. Browser local storage (`mentora-widget-boards-v1`) saves the selected board, cards, sizes, positions, artifact URLs, and a bounded conversation history. This release does not synchronize dashboards between browsers or accounts. Each browser supports 40 boards and each board 60 cards. Storage errors remain visible. Reloading an unfinished generation leaves a retry state rather than claiming completion.

The catalogue (`app/static/widget-catalog.json`) includes 27 existing `business-chart-recall` native components and all 18 official `trading-view-chart` widgets. Components are grouped by selection, diagnosis, market monitoring, financial analysis, flows/returns, and macro analysis. TradingView items carry their provider and widget type; market-wide tools accept optional scope rather than requiring a stock code. Manual native business-chart addition uses the existing `/api/chat/stream` research executor. Manual TradingView addition posts the selected widget, symbols, market, theme, and language to `/api/widgets/tradingview`, which calls the existing official renderer directly without any model or market-data request. The left chat composer sends dashboard context and the selected card to `/api/widgets/plan` for model planning. Validated actions can add or remove components, change parameters, rename the board, or adjust the 12-column layout. Selecting a card header scopes edits to that card; clearing selection scopes edits to the whole board. One-step Undo restores the preceding board snapshot. Layout-only edits preserve existing chart frames. Parameter changes use the direct TradingView renderer or the existing native research executor, using project skill routing and schema contracts. No sample market data, alternate renderer, or new financial execution path is introduced. Native artifact controls, source semantics, theme, and language remain inside their frames. The chart timestamp is the underlying artifact's data timestamp; generation is not a live refresh subscription.

Only same-origin generated/share-artifact HTML URLs are accepted. Generated files open through the existing share-artifact route. The existing nginx subpath rewriting supports `/mentora/`. The direct TradingView route requires the presentation service to load the new router. Requests and results stay attached to their originating board while switching tabs; deleting a pending card or board cannot resurrect it when the request completes.

Validation: `node --test tests/widgets.test.mjs tests/day-entry.test.mjs`. Browser checks include real manual AAPL cash-flow generation; conversational NVDA revenue-composition and EPS generation; desktop header dragging; pointer width/height resize; persistence after reload; and mobile layout.

The standalone stock-price / K-line and multi-intraday components are excluded from the Widget catalogue and conversational generation. Existing saved charts are retained; attempting to regenerate a removed K-line component displays an unavailable notice.

TradingView manual requests use the existing TradingView renderer directly with the exact widget type. The library is titled 图表库, with no search or subtitle. Stock-screening markets and economic-calendar regions are explicit dropdown choices; components without configurable parameters show no parameter field; no model interprets them. Group widgets use their native config shape; the display-only contract is preserved. Canvas iframe URLs include `canvas=1`, allowing newly generated TradingView HTML to fill a resized card with host titles and extra host footers hidden; the provider logo inside the embedded chart remains. Existing saved TradingView artifacts receive the same canvas-only wrapper adjustment. Standalone rendering remains unchanged.

Quote-list cards (`tv-market-data`) expose symbol chips above the hosted table. An explicit chip selection refreshes only single-symbol TradingView cards in that board, preserving interval, layout, and custom titles. Comparison groups, market-wide widgets and native Ainvest cards are not retargeted. If there are no compatible detail cards, one half-width advanced chart is added. The list itself stays mounted, selection persists, and Undo restores the previous snapshot. The hosted table's own links still open TradingView detail pages; no cross-origin DOM interception is used. Old cards recover their symbol metadata from their own saved `tv-config` document.

The 行情观察 library also exposes 日内分时图 (`tv-intraday`), a single-symbol preset of the existing official Symbol Overview widget. `/api/widgets/tradingview` accepts `preset: "intraday"` only for `widget: "symbol-overview"`, requires exactly one symbol, and defaults `dateRanges` to `1d|1` and the series to minute granularity. It retains theme, name lookup, persistence and Undo; metadata prevents it becoming the multi-symbol overview after reload. Explicit Skill config can override this preset's display settings.

## Shared TradingView config contract

Widget parameters accept `config`, identical to the pinned `trading-view-chart` Skill's `--config-json`. The Skill's `build_config` validates keys; the planner receives `configDefaults` and `configExtraKeys` from that same registry. Do not maintain a second indicator whitelist or invent unsupported configuration keys. Legacy convenience fields remain available, while explicit config takes precedence. Config patches merge by key; arrays are final lists except an explicit add request, which preserves existing study/comparison/watchlist entries. A convenience edit invalidates its corresponding stale config value. Full config survives imports from chat artifacts, edits, browser persistence, refresh and Undo.

For example, advanced-chart config `{ "style": "2", "studies": ["STD;EMA"], "hide_volume": true }` is passed to the same renderer as Skill output. Structured study entries are preserved, not converted to strings. Passing a value through is not proof that TradingView supports it: confirm official indicator IDs/input formats before claiming execution. The current Skill does not expose arbitrary Pine scripts or undocumented `studies_overrides`; those keys are rejected in both paths. Host theme, locale, size and provider availability follow the Skill's existing rules.

Historical native K-line controls receive the current native `kline-theme.css` at response time, including encoded child charts and inspiration cases. Saved OHLCV, annotations and period bindings remain intact; no prices are refreshed merely by opening an old report. The native business-chart repository remains the owner of the control style.
